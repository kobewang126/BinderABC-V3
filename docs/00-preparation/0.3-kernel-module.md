# 0.3 第一个 Linux 内核模块

## 0.3.1 这一节解决什么问题

前两节中，程序运行在用户态，通过系统调用请求内核提供服务。我们要逐步实现一个内核驱动，首先需要认识如何编译和加载一段内核代码。本节编写一个只打印加载和卸载消息的外部模块，不注册设备，也不实现 IPC。

目标是读懂模块的入口和退出函数，使用内核的构建系统生成 `.ko`，并在具备条件的实验环境中观察模块生命周期。如果还没有可用的模块实验环境，先阅读 [0.4 环境准备](0.4-kernel-environment.md)，再回来执行实验。

## 0.3.2 内核模块是什么

可加载内核模块是一种可由内核加载的目标文件，通常以 `.ko` 结尾。加载成功后，模块代码在内核中运行，拥有内核上下文的能力；它不是普通用户程序，也没有用户程序的 `main()`。加载和卸载分别触发模块指定的初始化与退出函数。模块发生严重错误可能影响整个运行中的系统，实验应在适合内核开发、可以恢复的环境进行。

## 0.3.3 阅读代码

配套 `examples` 仓库中的 `0.3/hello.c` 包含：

源码：`examples/0.3/hello.c`，第 5–17 行。

```c
static int __init binderabc_hello_init(void)
{
    pr_info("binderabc_hello: loaded\n");
    return 0;
}

static void __exit binderabc_hello_exit(void)
{
    pr_info("binderabc_hello: unloaded\n");
}

module_init(binderabc_hello_init);
module_exit(binderabc_hello_exit);
```

`module_init` 指定初始化函数；返回 0 表示初始化成功，负错误码表示失败。`module_exit` 指定卸载时的清理函数。`__init` 和 `__exit` 是内核的生命周期标记，由内核构建和加载机制处理；它们不是普通 C 程序的入口点。

`pr_info()` 将信息写入内核日志缓冲区。`MODULE_LICENSE("GPL")` 提供许可证元数据，影响内核如何处理模块及其可使用的导出符号；它本身不替代源码许可证文件。示例使用其他元数据帮助识别模块。

## 0.3.4 构建模块

需要运行 Linux、C 编译工具链及**与目标内核版本和配置匹配的已准备构建目录**。默认构建目标是当前运行内核：

```sh
cd examples/0.3
uname -r
test -d "/lib/modules/$(uname -r)/build" || echo "缺少当前内核构建目录"
make
modinfo ./binderabc_hello.ko
```

`examples` 是仓库目录名，可根据实际下载路径调整。构建成功后，`binderabc_hello.ko` 位于当前目录。`modinfo` 展示元数据和 `vermagic` 等信息，但不能单凭它保证模块能加载。没有 `modinfo` 时，通常需要安装发行版的 `kmod` 包。

Makefile 使用 `obj-m` 告诉 kbuild 构建外部模块，通过 `make -C ... M=... modules` 调用内核构建系统。`M` 指向模块源码目录，`KDIR` 指向目标内核构建目录。

`examples/0.3/Makefile` 中与构建有关的定义是：

源码：`examples/0.3/Makefile`，第 1–9 行。

```makefile
obj-m := binderabc_hello.o
binderabc_hello-y := hello.o

KDIR ?= /lib/modules/$(shell uname -r)/build
MODULE_DIR := $(CURDIR)

.PHONY: all clean
all:
	$(MAKE) -C $(KDIR) M=$(MODULE_DIR) modules
```

`obj-m` 指定模块名，`binderabc_hello-y` 指定组成它的 `hello.o`；因此源码叫 `hello.c`，最终模块却叫 `binderabc_hello.ko`。`KDIR ?=` 允许命令行覆盖默认目录；`-C` 让 Make 进入内核构建目录，`M` 告诉 kbuild 外部模块所在目录，`modules` 触发模块构建。这里使用的是内核构建系统，而不是直接用普通用户态链接命令生成 `.ko`。

若构建目录不在默认位置，可显式指定：

```sh
make KDIR=/path/to/matching/kernel-build
```

这只改变编译目标，不改变当前正在运行的内核；若该目录对应其他内核，得到的模块不能据此认为可在当前内核加载。

## 0.3.5 加载、查看和卸载

只有在确认模块针对当前内核构建、系统允许加载，并有相应权限时执行：

```sh
sudo insmod ./binderabc_hello.ko
lsmod | grep '^binderabc_hello '
sudo dmesg | tail -n 20
sudo rmmod binderabc_hello
sudo dmesg | tail -n 20
```

第一次日志中应能看到 `binderabc_hello: loaded`，卸载后应能看到 `binderabc_hello: unloaded`。内核日志是共享的环形缓冲区，可能包含其他消息；如有大量并发日志，`tail` 的行数可能需要增加。若模块已加载，重复 `insmod` 会失败；先确认状态。卸载命令使用模块名，而非 `.ko` 文件路径。

本节模块已在 Ubuntu 24.04、ARM64、Linux 6.8.0-147 环境中完成构建、加载、日志检查和卸载。

`insmod` 不会像 `modprobe` 那样自动解决模块依赖；本例没有额外模块依赖。运行 `make clean` 可清除本目录构建产物，使用自定义 `KDIR` 构建时清理也应传入相同的 `KDIR`。

## 0.3.6 常见问题

| 现象 | 检查方向 |
|---|---|
| `build` 目录不存在 | 安装或准备与目标内核匹配的构建目录，见 0.4。 |
| `Invalid module format` | 查看内核日志，检查内核版本、构建配置、架构和模块签名要求。 |
| `Operation not permitted` | 检查权限、模块加载策略及运行环境是否允许加载。 |
| 看不到日志 | 检查 `dmesg` 访问权限、内核日志及实际加载是否成功。 |

## 0.3.7 与 Binder 的联系

此模块只是进入内核代码的练习，没有字符设备、请求队列或跨进程调用。后续章节将用字符设备和文件操作把用户态请求接入我们设计的驱动。
