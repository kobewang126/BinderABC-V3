# 0.4 搭建 Linux 内核实验环境

## 0.4.1 这一节解决什么问题

后续需要编译、加载和调试自编写的内核模块。本节先建立一套可检查、可重复的实验流程：确认正在运行的内核、准备匹配的构建目录、验证构建工具，再运行 0.3 的模块。不同发行版和托管环境提供内核的方式不同，不能只根据发行版名称推断内核构建文件的位置。

## 0.4.2 确定实验环境

准备一个可以管理内核和加载模块的 Linux 实验环境。内核模块与普通程序不同，错误的模块可能导致内核崩溃或数据丢失；使用可恢复的实验系统，并保存重要数据。容器常常共享宿主机内核，容器内是 root 也不代表拥有模块加载权限；在共享内核的环境中，模块操作会影响共享该内核的其他工作负载。

本教程的命令以 Linux shell 为例，不要求特定宿主机或虚拟化产品。构建用户态示例只需 C 编译器和 Make；0.3 和后续驱动还需要匹配的内核构建目录及模块管理工具。

### 0.4.2.1 本教程的验证环境

本教程目前使用 **Multipass 创建的 Linux 虚拟机**验证内核实验。一次已验证的环境如下；这些是验证记录，不是读者必须使用的唯一配置：

| 项目 | 本教程的环境 |
|---|---|
| 虚拟化工具 | Multipass |
| 虚拟化驱动 | `applevz`（Apple Virtualization framework） |
| 虚拟机系统 | Ubuntu 24.04 LTS，ARM64 |
| 虚拟机资源 | 2 个虚拟 CPU、2 GB 内存、15 GB 磁盘 |
| 验证时运行的内核 | `6.8.0-147-generic`，架构 `aarch64` |
| 模块构建文件 | 与运行内核匹配的 `linux-headers-6.8.0-147-generic` |

虚拟机系统更新或选择不同镜像后，运行的内核版本可能不同。安装头文件时应使用自己环境里的 `uname -r`，不要照抄表中的版本号。

如果选择 Multipass，需要先在宿主机安装 Multipass，安装方法见 [Multipass 官方安装文档](https://documentation.ubuntu.com/multipass/latest/how-to-guides/install-multipass/)。在支持 Apple Virtualization 的 macOS 上，新建实例前可在**宿主机终端**选择本教程使用的驱动：

```sh
multipass set local.driver=applevz
```

驱动是 Multipass 的宿主机配置；若已有实例，先查阅官方说明并确认现有实例与驱动的兼容性，不必为了阅读教程更改正在使用的环境。接下来可以在**宿主机终端**创建并进入一个 Ubuntu 实验环境：

```sh
multipass launch 24.04 --name binder-lab --cpus 2 --memory 2G --disk 15G
multipass info binder-lab
multipass shell binder-lab
```

已有同名实例时不需要重新创建，直接使用 `multipass shell binder-lab` 进入。之后的 `apt`、`make`、模块加载和实验程序都在**虚拟机内的 Linux shell**运行。完成后可用 `exit` 返回宿主机终端；也可以从宿主机用 `multipass exec binder-lab -- uname -r` 查询虚拟机内核。

读者也可以使用满足模块加载条件的其他 Linux 环境，直接执行下面的 Linux 命令，无需安装 Multipass。源码仓库或压缩包需要放在运行实验的 Linux 环境中；本教程的章节命令从对应的 `examples` 源码目录执行。

## 0.4.3 检查运行内核和工具

```sh
uname -r
uname -m
cat /proc/version
command -v gcc
command -v make
command -v git
command -v insmod
command -v modinfo
ls -ld "/lib/modules/$(uname -r)/build"
```

`uname -r` 是当前运行的内核版本，`uname -m` 是机器架构，`/proc/version` 可帮助了解构建该内核的编译器。`build` 一般指向发行版提供的内核构建目录；如果不存在，需要从**当前内核的提供方**获取匹配的构建文件。仅有 `/usr/include/linux` 或 `linux-libc-dev` 并不等于具备外部模块构建环境。

还可以检查内核是否禁止继续加载模块：

```sh
cat /proc/sys/kernel/modules_disabled
```

值为 `1` 时不应尝试加载；值为 `0` 也不保证有权限或满足签名等策略。不要修改这个开关来绕过环境限制。

## 0.4.4 安装基础工具

在 Debian 或 Ubuntu 的常规发行版内核环境中，使用 **Linux 环境内的终端**安装用户态开发与模块管理工具：

```sh
sudo apt update
sudo apt install build-essential git kmod strace
```

`build-essential` 提供 GCC、Make 等构建工具；`git` 用于获取和管理源码；`kmod` 提供 `insmod`、`rmmod`、`modinfo` 等模块工具；`strace` 用于观察用户态系统调用。使用源码压缩包的读者不依赖 Git，也可以不安装 `git`。需要调试用户态程序时，可额外安装 `gdb`：

```sh
sudo apt install gdb
```

如果内核由发行版提供，并且该版本的头文件包仍可从已配置的软件源获取，可以尝试：

```sh
sudo apt install "linux-headers-$(uname -r)"
```

安装后再次检查 `/lib/modules/$(uname -r)/build`。如果找不到对应包，不要用不同版本的头文件冒充：某些环境运行的是定制内核，需要向内核提供方获取与其实际构建一致的构建树、配置和必要的构建产物。其他发行版应使用其文档提供的对应开发包。

### 0.4.4.1 出错时先定位到哪一层？

| 检查结果 | 下一步 |
|---|---|
| `command -v gcc` 或 `make` 无输出 | 安装对应编译工具，再重新检查。 |
| `build` 路径不存在 | 对照 `uname -r` 查找当前内核提供方的开发包或构建产物。 |
| `make` 成功，`insmod` 失败 | 查看命令错误与内核日志，排查版本、架构、符号、签名和权限。 |
| `insmod` 成功，日志不可读 | 确认日志读取权限和内核日志策略；不能仅凭看不到日志断定模块未加载。 |

优先检查 `uname -r`，再决定要安装什么头文件。发行版版本号和运行内核版本是不同的信息，安装另一版本的开发包并不会替换运行中的内核。

## 0.4.5 构建目录需要什么

外部模块需要内核构建系统及目标内核的配置、生成头文件等，不是只需要几份 `.h` 文件。若启用了符号版本校验，通常还需要与目标内核相符的 `Module.symvers`；仅运行 `make modules_prepare` 不会生成它。签名强制策略、架构或编译器差异也可能影响加载。发行版的对应内核开发包通常已处理这些准备工作，定制内核则应按照内核提供方的构建说明准备。

本教程暂不要求读者自行编译或替换正在运行的内核。如果另行从源码构建内核，使用相同源码、配置和构建产物构建外部模块，并确保运行的确实是对应内核；单独准备一棵源码树并不会改变当前运行内核。

## 0.4.6 验收实验

完成前述准备后，执行 [0.3](0.3-kernel-module.md) 的构建、加载、日志检查与卸载步骤。建议记录：

- `uname -r` 和 `uname -m` 的结果；
- 实际使用的内核构建目录以及 `modinfo` 显示的信息；
- 加载和卸载时的内核日志，以及两个命令的退出状态。

只有 `.ko` 编译成功，说明构建流程通过；只有在目标内核上完成加载、观察日志和卸载，才说明该环境的模块实验通过。`dmesg` 权限不足、模块签名策略、缺少权限或内核配置都可能阻止后一步，具体原因需结合命令错误和内核日志排查。
