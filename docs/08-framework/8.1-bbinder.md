# 8.1 BBinder：把本地对象统一成 transact 调用

7.4 的计算器服务仍在 `main()` 中判断 code、读参数、执行加减并拼接回复。若一个进程中有多种对象，能不能让每个对象自己处理事务，而把通信循环留给公共代码？

第八篇分四步完成用户态库：8.1 先做本地 `BBinder`；8.2 用 `ProcessState` 管理连接；8.3 用 `IPCThreadState` 处理线程通信；8.4 再用 `BpBinder` 表示远端对象。本章没有远程调用，也不打开设备，源码是独立的 `examples/8.1/`，无需加载模块。

## 8.1.1 从 C 的函数表到 C++ 虚函数

第三篇已经用结构体和函数指针表示对象。这里改用少量 C++：`class` 把数据和函数放在一起；`public` 是可调用入口；`protected` 留给派生类实现；`virtual` 允许通过基类接口执行派生类函数，类似前面的函数指针表。`override` 让编译器检查是否正确重写了入口；`final` 则阻止再重写该入口。

本章使用 C++17，读者只需理解这里出现的语法。`status_t` 是 `int` 的别名，约定 0 成功、负 errno 表示错误；真正的业务结果放在 reply Parcel 中，不能把加法结果当作状态码返回。

源码：`examples/8.1/framework/binder.h`，第 25–35 行（封装版本 `8.1`，节选）。

```cpp
class IBinder {
public:
    virtual ~IBinder() = default;
    virtual status_t transact(uint32_t code, Parcel &data, Parcel *reply) = 0;
};
class BBinder : public IBinder {
public:
    status_t transact(uint32_t code, Parcel &data, Parcel *reply) final;
protected:
    virtual status_t onTransact(uint32_t code, Parcel &data, Parcel *reply);
};
```

`IBinder` 是统一的调用接口，不提供业务实现；`BBinder` 表示当前进程中的本地对象，把公共入口 `transact()` 转到可重写的 `onTransact()`。两者的虚析构函数使基类对象的销毁遵守 C++ 的多态规则。本章暂时不讨论远端代理和内核 Node。

```mermaid
flowchart LR
    C[调用者] --> I[IBinder 接口]
    I --> B[BBinder transact]
    B --> O[Calculator onTransact]
    O --> P[参数与回复 Parcel]
```

## 8.1.2 公共入口与业务入口怎样分开？

源码：`examples/8.1/framework/binder.cpp`，第 41–44 行（封装版本 `8.1`，节选）。

```cpp
status_t BBinder::transact(uint32_t code, Parcel &data, Parcel *reply) {
    if (!reply) return -EINVAL;
    return onTransact(code, data, reply);
}
```

公共入口先拒绝空回复指针，再进行虚函数分发。默认 `BBinder::onTransact()` 返回 `-ENOSYS`；计算器派生类根据 code 实现加减。这里没有 ioctl，函数就在当前调用线程里执行。

源码：`examples/8.1/framework/calculator.h`，第 8–16 行（封装版本 `8.1`，节选）。

```cpp
class Calculator final : public BBinder {
protected:
    status_t onTransact(uint32_t code, Parcel &data, Parcel *reply) override {
        if (code != kAdd && code != kSubtract) return -ENOSYS;
        uint32_t a, b;
        if (data.readU32(&a) || data.readU32(&b) || !data.atEnd()) return -EINVAL;
        return reply->writeU32(code == kAdd ? a + b : a - b);
    }
};
```

计算器先检查 code，再读取两个整数，并要求读游标到达负载末尾，避免默默接受截断或多余参数。整数仍按前面章节的无符号 32 位规则计算；本章没有改变溢出语义。调用一次会推进 data 的读游标，示例每次构造新的请求 Parcel。

## 8.1.3 Parcel 为什么先只包一层？

本章的 C++ `Parcel` 用固定数组持有 256 字节，通过临时 C `parcel` 视图调用已经验证过的编解码函数。C 文件仍由 C 编译器编译，头文件放在 `extern "C"` 中声明，避免改变链接名称；没有另写一套整数或字符串格式。

源码：`examples/8.1/framework/binder.cpp`，第 12–17 行（封装版本 `8.1`，节选）。

```cpp
status_t Parcel::writeU32(uint32_t value) {
    auto p = view();
    if (parcel_write_u32(&p, value)) return -ENOSPC;
    size_ = p.size;
    return 0;
}
```

`auto p = view()` 得到借用本对象数组的 C 视图；编码成功后把长度写回。读取也沿用 C 解码器，只更新当前 Parcel 的读位置。`std::array` 自己持有字节，不依赖调用方另外维持缓冲区。完整实现和边界实验分别在 `framework/binder.cpp`、`tests/local_test.cpp`。

## 8.1.4 实验：同一个接口调用加法和减法

Linux 需要 GCC/G++、Make；本章没有内核构建要求：

```sh
cd examples/8.1
make
./build/local_demo
./build/local_test
```

Ubuntu 24.04 ARM64 上实际输出：

```text
local BBinder add(7, 3) = 10
local BBinder sub(7, 3) = 4
local dispatch, malformed arguments and reused C Parcel boundaries passed
```

`local_demo` 把 `Calculator` 当作 `IBinder &` 使用，调用者不直接调用计算函数；派生类最终仍在本进程执行。附加验收检查未知 code、空回复、缺失或多余参数，以及字符串和容量边界。源码没有设备 open/ioctl，因而通过本实验不能证明跨进程通信已经实现。
