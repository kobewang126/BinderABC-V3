# 2.5 用 code 选择服务方法

## 2.5.1 一个服务，多个操作

第 2.4 章的服务端收到 Parcel 后执行固定逻辑。如果一个计算器服务同时提供加、减、乘、除，客户端除了传入参数，还需要告诉服务端选择哪个操作。本章启用事务中预留的 `code`，由服务端根据它调用相应函数。

完整代码在 `examples/2.5/`，协议版本显示为 `0205`。本章启用之前预留的 `code` 字段，应使用同一章节的驱动和程序。

## 2.5.2 方法 code 放在哪里？

源码：`examples/2.5/include/mini_binder.h`，第 13–26 行。

~~~c
struct mini_binder_transaction_data {
    __u64 id;
    __u32 size;
    __s32 status;
    __u32 code;
    __u8 data[MINI_BINDER_MAX_DATA];
};

enum mini_binder_calc_cmd {
    MINI_CALC_ADD = 1,
    MINI_CALC_SUB = 2,
    MINI_CALC_MUL = 3,
    MINI_CALC_DIV = 4,
};
~~~

`code` 表示一个服务对象上的操作；请求中的 `id` 由驱动生成，用于关联本次请求和回复，不是操作码。这里的 `code` 对应 Android Binder 事务数据中 `code` 的教学概念；它也不是 `MINI_BINDER_TRANSACT_MAPPED` 这种告诉驱动执行哪种操作的 ioctl 命令。

本章尚无目标 handle：驱动仍只有一个已注册服务端。后面需要将“handle 选择对象”和“code 选择对象上的操作”组合起来。

## 2.5.3 从客户端交给驱动

源码：`examples/2.5/userspace/calc_ipc.h`，第 11–24 行。

~~~c
static int calc_transact(int fd, void *mapping, size_t page_size,
                         __u32 code, int32_t a, int32_t b, int32_t *result)
{
    struct mini_binder_transaction_data tx = { .code = code };
    struct parcel p;
    uint32_t bits_a, bits_b, bits_result;
    int status;

    memcpy(&bits_a, &a, sizeof(a));
    memcpy(&bits_b, &b, sizeof(b));
    parcel_init(&p, tx.data, sizeof(tx.data));
    if (parcel_write_u32(&p, bits_a) || parcel_write_u32(&p, bits_b)) return -EINVAL;
    tx.size = (__u32)p.size;
    if (ioctl(fd, MINI_BINDER_TRANSACT_MAPPED, &tx) < 0) return -errno;
~~~

客户端把方法 code 写到事务元数据，两个有符号 32 位参数以相应的 32 位表示写入 Parcel。这里的 `memcpy` 保留整数的位模式，Parcel 的整数按小端编码；该教学协议不是 Android Parcel 格式。

源码：`examples/2.5/kernel/mini_binder.c`，第 129–136 行。

~~~c
    server_ctx = server_file->private_data;
    memcpy(server_ctx->buffer, transaction.data, transaction.size);
~~~

驱动负责保存并转交命令，不负责决定加减乘除。服务端通过 `RECEIVE_TRANSACTION` 获取请求元数据，再从映射页读取参数。

## 2.5.4 服务端分发和返回

源码：`examples/2.5/userspace/calc_server.c`，第 38–54 行。

~~~c
static int calculate(__u32 code, int32_t a, int32_t b, int32_t *result)
{
    int64_t value;
    int status;

    switch (code) {
    case MINI_CALC_ADD: status = add(a, b, &value); break;
    case MINI_CALC_SUB: status = subtract(a, b, &value); break;
    case MINI_CALC_MUL: status = multiply(a, b, &value); break;
    case MINI_CALC_DIV: status = divide(a, b, &value); break;
    default: return -ENOTTY;
    }
    if (status) return status;
    if (value < INT32_MIN || value > INT32_MAX) return -ERANGE;
    *result = (int32_t)value;
    return 0;
}
~~~

四个分支调用独立函数；结果先用 `int64_t` 计算，检查是否能放回 `int32_t`。除数为零返回 `-EDOM`；包括 `INT32_MIN / -1` 在内的结果溢出返回 `-ERANGE`；未知命令返回 `-ENOTTY`。整数除法向零截断，例如 `-7 / 3 = -2`。

源码：`examples/2.5/userspace/calc_server.c`，第 77–95 行（节选）。

参数格式错误返回 `-EINVAL`。正常结果写入回复 Parcel；服务端错误放在事务的 `status` 中，和 ioctl 本身失败区分开。客户端无论收到成功还是服务端错误，都要释放本次映射回复槽，才能继续使用同一个文件发起映射事务。

下图展示一次正常调用，客户端和服务端已分别完成映射。请求的 `code` 随元数据复制给服务端，Parcel 请求和回复分别从各自接收方的映射页读取：

~~~mermaid
sequenceDiagram
    participant C as 客户端（用户态）
    participant K as mini-binder（内核态）
    participant S as 计算器服务（用户态）
    S->>K: RECEIVE_TRANSACTION，等待请求
    Note over C: mini_binder_transaction_data<br/>code + 请求 Parcel
    C->>K: TRANSACT_MAPPED：copy_from_user 复制事务结构
    Note over K: 保存 code 和请求元数据
    K->>K: memcpy 请求 Parcel 到服务端映射页，唤醒服务端
    Note over K: mini_binder_transaction_data<br/>接收请求的元数据，包含 code
    K->>S: RECEIVE_TRANSACTION 返回：copy_to_user 复制事务结构
    Note over C,K: 客户端等待回复
    S->>S: 读取映射页中的请求 Parcel<br/>无需 copy_to_user 复制请求载荷
    S->>S: 根据 code 分派到计算函数
    Note over S: mini_binder_transaction_data<br/>状态 + 回复 Parcel
    S->>K: TRANSACTION_REPLY：copy_from_user 复制回复结构
    K->>K: 保存回复并唤醒客户端，memcpy 回复到客户端映射页
    K->>C: TRANSACT_MAPPED 返回：copy_to_user 复制事务结构
    C->>C: 读取映射页中的回复 Parcel<br/>无需 copy_to_user 复制回复载荷
    Note over C: mini_binder_transaction_data<br/>包含回复状态和长度
    C->>K: RELEASE_REPLY，允许回复槽复用
~~~

图中展示的是映射回复路径。驱动只转交 `code`，不调用计算函数；`copy_to_user()` 仍会复制完整事务结构，客户端读取的回复载荷位于映射页。

## 2.5.5 实验

需要支持加载模块的 Linux 环境、匹配当前内核的构建目录和加载权限。先停止其他章节服务端并卸载已加载的 `mini_binder`。

终端一：

~~~sh
cd examples/2.5
make
sudo insmod kernel/mini_binder.ko
./build/version
./build/calc_server
~~~

在 Ubuntu 24.04 ARM64、Linux 6.8.0-147 上实际输出：

~~~text
mini-binder protocol version: 0205
calculator server ready
~~~

保持服务端运行，在终端二：

~~~sh
cd examples/2.5
./build/calc_client add 7 3
./build/calc_client sub 7 3
./build/calc_client mul 7 3
./build/calc_client div -7 3
./build/calc_test
~~~

实际输出：

~~~text
add(7, 3) = 10
sub(7, 3) = 4
mul(7, 3) = 21
div(-7, 3) = -2
arithmetic commands and error recovery passed
~~~

`calc_test` 还通过驱动验证除零、未知命令、加法与乘法溢出、除法溢出、截断请求及错误后的继续调用。停止服务端后，执行 `sudo rmmod mini_binder`。计算器服务与旧 `transaction_server` 使用不同 Parcel 格式，必须与各自客户端配对。

## 2.5.6 限制和下一步

目前只有一个服务端、一笔在途事务，没有 handle、对象传递、超时或服务发现。客户端回复使用第 2.4 章的映射页，服务端仍需把回复数据提交给驱动，不是完全零拷贝。下一章[引入 BC 和 BR 命令](2.6-bc-br.md)。
