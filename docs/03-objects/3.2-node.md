# 3.2 在驱动中表示服务对象

本章显式创建 Node，是为了先观察“用户态对象在驱动中有了身份”。这是临时教学接口，3.5～6.4 的独立实验仍用返回的 Node 编号引导首次通信；[7.1](../07-protocol/7.1-auto-node.md) 会删除 CREATE_NODE 和参数结构，后续章节不再沿用。Node 本身也不是跨进程公开的全局调用凭据。

## 3.2.1 上一章的编号属于谁？

第 3.1 章的编号只由服务端用户态查表解释。驱动不知道编号是否对应对象，也不知道对象属于哪个服务端。本章为两个用户态对象各创建一个内核 Node：Node 保存所属服务端文件和一个用户态 `cookie`，由驱动分配编号。

客户端暂时直接使用实验中获知的 Node 编号。它不是 Binder handle，也没有访问控制或引用传递语义；本章先观察 Node 和用户态对象如何对应。源码位于 `examples/3.2/`，版本显示为 `0302`。

## 3.2.2 Node 和用户态对象

```text
客户端                         驱动                              服务端
用户态                         内核态                            用户态

target_node = 1 ─────────────> Node 1 ── owner ──────────────> 已打开的服务端文件
                                  └──── cookie ──────────────> 加法对象 ── invoke ──> add

target_node = 2 ─────────────> Node 2 ── owner ──────────────> 同一个服务端文件
                                  └──── cookie ──────────────> 乘法对象 ── invoke ──> multiply
```

`cookie` 是服务端给驱动保存的用户态标识；驱动不会解引用它，也不会执行函数指针。服务端收到请求后，检查 `cookie` 是否对应自己的已知对象，再在用户态调用对象的 `invoke`。本图中 1、2 只是首次加载模块后的示例编号，服务端重启后编号可能不同。

源码：`examples/3.2/kernel/mini_binder.c`，第 33–37、44–48 行（节选）。

```c
struct mini_binder_node {
    __u64 id;
    __u64 cookie;
    struct file *owner;
};
/* ... */
static struct file *server_file;
static struct transaction_slot slots[SLOT_COUNT];
static __u64 next_id;
static struct mini_binder_node nodes[2];
static __u64 next_node_id;
```

`owner` 关联已注册服务端的打开文件；`nodes` 是最多两个对象的全局教学表，`state_lock` 保护它。真实 Binder 的 `binder_node` 关联 `binder_proc`，并维护引用和生命周期信息；本章只保留理解对象归属所需的最小字段。

## 3.2.3 服务端创建两个 Node

源码：`examples/3.2/userspace/object_server.c`，第 51–57 行（节选）。

```c
    if (fd < 0 || page_size < MINI_BINDER_MAX_DATA) { perror("open or page size"); return 1; }
    if (ioctl(fd, MINI_BINDER_REGISTER_SERVER) < 0) { perror("register server"); close(fd); return 1; }
    for (unsigned int i = 0; i < sizeof(objects) / sizeof(objects[0]); i++) {
        struct mini_binder_node_create node = { .cookie = (__u64)(uintptr_t)&objects[i] };
        if (ioctl(fd, MINI_BINDER_CREATE_NODE, &node) < 0) { perror("create node"); close(fd); return 1; }
        printf("object %u: node=%llu\n", objects[i].id, (unsigned long long)node.node_id);
    }
```

服务端将各自对象地址作为 `cookie` 提交，驱动返回 Node 编号。服务端进程的静态对象在整个服务期间有效；驱动不验证任意用户地址是否是合法对象，服务端后续也只接受自己已知的两个地址。

源码：`examples/3.2/kernel/mini_binder.c`，第 56–73 行（节选）。

```c
    if (copy_from_user(&create, arg, sizeof(create))) return -EFAULT;
    if (!create.cookie) return -EINVAL;
    mutex_lock(&state_lock);
    if (server_file != file) { ret = -EPERM; goto out; }
    for (i = 0; i < ARRAY_SIZE(nodes); i++) {
        if (nodes[i].owner && nodes[i].cookie == create.cookie) { ret = -EEXIST; goto out; }
        if (!nodes[i].owner) break;
    }
    if (i == ARRAY_SIZE(nodes)) { ret = -ENOSPC; goto out; }
    if (next_node_id == U64_MAX) { ret = -EOVERFLOW; goto out; }
    create.node_id = next_node_id + 1;
    if (copy_to_user(arg, &create, sizeof(create))) { ret = -EFAULT; goto out; }
    nodes[i].id = ++next_node_id;
    nodes[i].cookie = create.cookie;
    nodes[i].owner = file;
out:
    mutex_unlock(&state_lock);
    return ret;
```

只有已注册的服务端文件能创建 Node。空 cookie、重复对象、容量耗尽、无效用户地址和编号耗尽分别返回错误。服务端文件释放时驱动清除 Node 表；编号在模块加载期间递增，因此重启服务端后旧编号不能代表新对象。

## 3.2.4 从 Node 找到用户态对象

源码：`examples/3.2/kernel/mini_binder.c`，第 217–225 行（节选）。

```c
    if (transaction.target_node) {
        for (i = 0; i < ARRAY_SIZE(nodes); i++)
            if (nodes[i].owner == server_file && nodes[i].id == transaction.target_node)
                break;
        if (i == ARRAY_SIZE(nodes)) { ret = -ENOENT; goto unlock_state; }
        transaction.object_cookie = nodes[i].cookie;
    } else {
        transaction.object_cookie = 0;
    }
```

驱动在 `state_lock` 下查找属于当前服务端的 Node，把保存的 `cookie` 放入事务，随后发布请求。找不到目标立即返回 `ENOENT`。`target_node == 0` 是为了保留上一章不按对象寻址的实验路径，本章不把它称为 ServiceManager 的 handle 0。

源码：`examples/3.2/userspace/object_server.c`，第 37–44 行。

```c
static const struct service_object objects[] = {{1, add}, {2, multiply}};

static int dispatch(__u64 cookie, __u32 code, int32_t a, int32_t b, int32_t *result)
{
    for (unsigned int i = 0; i < sizeof(objects) / sizeof(objects[0]); i++)
        if ((__u64)(uintptr_t)&objects[i] == cookie) return objects[i].invoke(code, a, b, result);
    return -ENOENT;
}
```

驱动返回 `cookie` 后，服务端先与自己已知对象的地址比较，不直接解引用不可信地址。匹配后才根据事务 `code` 调用函数。Node 编号选择对象，事务 `id` 匹配请求和回复，`code` 选择操作；三者用途不同。

## 3.2.5 构建与实验

先停止其他章节的服务端并卸载旧模块。在终端一：

```sh
cd examples/3.2
make
sudo insmod kernel/mini_binder.ko
./build/version
./build/object_server
```

在 Ubuntu 24.04 ARM64、Linux 6.8.0-147 上，首次加载模块后实际输出：

```text
mini-binder protocol version: 0302
object 1: node=1
object 2: node=2
object server ready
```

在终端二使用服务端输出的 Node 编号。以下数字仅对应上面的首次运行；如果服务端重启，请替换为它新打印的编号。

```sh
cd examples/3.2
./build/object_client 1 add 7 3
./build/object_client 2 mul 7 3
```

实际输出：

```text
add(7, 3) = 10
mul(7, 3) = 21
```

停止服务端后，可运行 `timeout 10 ./build/node_test`，检查 Node 创建权限、重复创建和容量；该测试自行注册服务端。完成后执行 `sudo rmmod mini_binder` 和 `make clean`。

## 3.2.6 限制和下一步

Node 表最多两个，只支持一个服务端；编号靠人工告知客户端，不是受保护的引用，不能作为安全边界。服务端退出时 Node 随之清除，不实现引用计数和死亡通知；对象地址不跨进程使用。真实 Binder 不通过本章自定义 `CREATE_NODE` 协议让客户端直接使用全局 Node 编号。

下一章先学习如何在 Parcel 中描述对象，让驱动能够区分普通数据和需要特殊处理的对象。
