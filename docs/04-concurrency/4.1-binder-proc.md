# 4.1 一个 Binder 上下文有哪些对象？

## 4.1.1 问题与设计

第三篇中，每次打开设备都得到一个文件私有上下文，里面有映射和 Ref 表；Node 则记录所属文件。对象多起来后，驱动需要一个更明确的容器，说明这些信息属于谁。

本章把文件上下文整理为 `mini_binder_proc`，用独立的 `mini_binder_ref` 表示引用，并让 Node 直接指向所属 proc。Ref 暂时仍以 Node ID 找到 Node，事务行为沿用 3.6。源码在 `examples/4.1/`，协议版本 `0401`。

```mermaid
flowchart LR
    A[客户端 proc] --> R[Ref: Node ID]
    R --> N[Node]
    N --> B[服务端 proc]
    B --> O[服务端用户态对象]
```

## 4.1.2 proc、Ref 与 Node

源码：`examples/4.1/kernel/mini_binder.c`，第 19–33、42–46 行（节选）。

```c
struct mini_binder_ref {
    __u64 node_id;
};

struct mini_binder_proc {
    struct file *file;
    bool is_server;
    void *buffer;
    struct vm_area_struct *server_vma;
    bool inflight;
    bool reply_ready;
    bool reply_delivered;
    struct mini_binder_ref refs[MINI_BINDER_MAX_OBJECTS];
    struct mini_binder_transaction_data pending_reply;
};

/* ... */

struct mini_binder_node {
    __u64 id;
    __u64 cookie;
    struct mini_binder_proc *owner;
};
```

proc 保存映射和 Ref 表；handle 仍是表下标加一。Node 的 `owner` 指向创建它的 proc，`cookie` 供该进程在用户态找到对象。Node 存在固定的全局数组中，不是 Android 的 proc Node 红黑树。

源码：`examples/4.1/kernel/mini_binder.c`，第 171–182 行（完整函数）。

```c
static int mini_binder_open(struct inode *inode, struct file *file)
{
    struct mini_binder_proc *ctx;

    (void)inode;
    ctx = kzalloc(sizeof(*ctx), GFP_KERNEL);
    if (!ctx)
        return -ENOMEM;
    ctx->file = file;
    file->private_data = ctx;
    return 0;
}
```

每次独立 `open()` 分配一个 proc；分配失败返回 `ENOMEM`。`dup()` 和 `fork()` 共享同一个打开文件，因此共享它的 proc 和 Ref 表。映射也持有文件引用，所以关闭一个描述符不一定立即销毁 proc。

## 4.1.3 从 handle 找到服务端

源码：`examples/4.1/kernel/mini_binder.c`，第 307–318 行（节选）。

```c
    if (transaction.target_handle) {
        if (transaction.target_node || transaction.target_handle > ARRAY_SIZE(client_ctx->refs) ||
            !client_ctx->refs[transaction.target_handle - 1].node_id) { ret = -ENOENT; goto unlock_state; }
        transaction.target_node = client_ctx->refs[transaction.target_handle - 1].node_id;
    }
    if (transaction.target_node) {
        for (i = 0; i < ARRAY_SIZE(nodes); i++)
            if (nodes[i].owner && nodes[i].id == transaction.target_node)
                break;
        if (i == ARRAY_SIZE(nodes)) { ret = -ENOENT; goto unlock_state; }
        transaction.object_cookie = nodes[i].cookie;
        receiver = nodes[i].owner->file;
```

驱动先查调用方 proc 的 Ref，再按 ID 查 Node，通过 Node 的 owner 找接收文件。`state_lock` 保护 Node、Ref 和事务状态；映射状态由 `mapping_lock` 保护。服务端的最后一个文件引用释放时，驱动在状态锁下清除它的 Node，标记相关未取走事务失败，再唤醒客户端；旧 Ref 不保活 Node，后续调用会失败。

## 4.1.4 实验

在支持加载模块且有匹配内核头文件的 Linux 环境中，先停止其他章节服务端并卸载旧模块。

终端一：

```sh
cd examples/4.1
make
sudo insmod kernel/mini_binder.ko
./build/version
./build/object_server
```

终端二：

```sh
cd examples/4.1
./build/ref_test
```

在 Ubuntu 24.04 ARM64、Linux 6.8.0-147 上的实际输出：

```text
mini-binder protocol version: 0401
file A: handle 1, add(7, 3) = 10
file B: handle 1, mul(7, 3) = 21
dup A: handle 1, add(8, 4) = 12
independent proc refs and dup shared refs passed
```

测试中两个独立打开文件各有 handle 1，分别指向不同 Node；`dup()` 后的新描述符复用原文件的 Ref。另已运行对象传递、多服务端、服务端退出和取消回归。结束时停止服务端并执行 `sudo rmmod mini_binder`。

## 4.1.5 限制与自测

本章的 proc 是按打开文件分配的教学上下文，没有线程表、工作队列、引用计数或死亡通知；不能把它当成完整 Android `binder_proc`。Ref 通过 ID 而不是指针找到 Node，容量固定。直接 Node 编号和临时查询入口依然保留，并非安全边界。

1. 两次独立 `open()` 和一次 `dup()` 各自如何影响 Ref 表？
2. 为什么 Node 的 owner 和 Ref 所属 proc 可以不同？
3. 服务端退出后为什么旧 handle 不一定仍能调用？

参考：独立打开产生独立上下文，dup 共享；owner 是对象拥有者，Ref 属于引用持有者；退出清除 Node，Ref 不保活它。
