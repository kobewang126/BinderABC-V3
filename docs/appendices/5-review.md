# 第五篇自测

## 题目

1. 两个调用线程共享一个 proc 时，为什么分别保存状态还需要不同的回复位置？
2. 5.1 的 `reply_offset` 指向哪里？它与 Parcel 对象位置表是否相同？
3. proc todo 和 thread todo 分别交给谁？事务槽为什么需要记录调用线程？
4. 5.2 删除公开事务 id 后，BC_REPLY 如何找到调用者？为什么另一个服务线程不能代回？
5. 服务线程领取请求后显式退出，PROCESSING 与 CANCELLED 两种状态如何清理？
6. 5.4 中普通上下文怎样提供本地对象？为什么用户态要明确选择读取请求还是回复？
7. 定向唤醒日志和调度事件各能说明什么？
8. 线程没有发送退出命令就终止，本例是否自动处理？

## 参考答案

1. 线程状态分开后，回复载荷仍可能互相覆盖；各自保留映射位置才能并存并独立释放。
2. 它是回复载荷在本例共享映射中的位置；对象位置表标识 Parcel 内需要转换的对象，含义不同。
3. proc todo 的请求由目标服务线程领取，thread todo 的回复由发起调用的线程领取；调用线程指针决定回复归属和唤醒目标。
4. 当前服务线程的 current_transaction 指向待回复事务，再由事务的 caller 找调用线程；其他线程没有该绑定，不能靠共享 fd 代回。
5. PROCESSING 标为 FAILED 并唤醒调用者，由调用者返回 EPIPE 后收尾；CANCELLED 已没有等待者，可以直接归还槽。两种路径都先清除服务线程绑定，再回收记录。
6. 创建 Node、建立映射并安排线程读取请求；同一上下文可发送和接收，因此 READ 需要显式指出本次领取请求还是回复。
7. 日志记录选择的唤醒目标；受控区间的调度事件记录实际唤醒，不能排除其他负载或信号导致的唤醒。
8. 不会自动检测，必须显式退出；整个 proc 最终释放仍会统一清理剩余资源。
