# 第五篇自测

## 题目

1. 为什么服务进程打开一次设备后，两个服务线程可以共用 fd？每个线程仍需独立保存什么？
2. 5.1 的线程身份记录是否已经允许同一 fd 同时发起两个调用？
3. proc.todo 与 server_wait 的职责有什么不同？
4. 服务线程为什么先释放 state_lock 再等待？两个线程同时醒来，为什么不会处理同一请求？
5. 5.2 的两个服务线程共用 fd，但两个调用线程为什么暂时分别 open？
6. 5.3 为什么既要拆分调用状态，也要预留独立回复位置？reply_offset 与对象位置表是否相同？
7. 5.4 删除公开 id 后，BC_REPLY 怎样找到原调用者？其他线程能否代回？
8. 屏障、proc 状态观察和定向唤醒的 tracefs 事件各能验证什么？

## 参考答案

1. 同一进程的线程共享文件描述符表；proc、Ref 表和映射共享，线程身份以及后续的调用状态和当前事务绑定分别记录。
2. 没有，5.1 只记录身份，调用状态和回复仍按文件保存。
3. proc.todo 保存未领取的普通请求，server_wait 负责等待与唤醒；有工作不等于已分配给某个线程。
4. 提交方也需要状态锁才能入队；领取方持锁从队列移除事务，另一个线程无法再次领取。
5. 当时调用状态和回复仍按打开文件共享；各自 open 才能让两个调用同时在途，服务端领取队列则由共同 proc 管理。
6. 只拆分状态仍会覆盖回复数据；回复位置在映射偏移 512/768，reply_offset 定位回复载荷，对象位置表标识 Parcel 中的对象条目。
7. 当前服务线程的 current_transaction 指向它领取的事务，再沿 caller 找到调用线程；其他线程没有该绑定，不能代回。
8. 屏障构造受控并发；proc 状态确认特定时刻在 ioctl 中睡眠；调度事件观察实际唤醒目标。它们不能证明公平调度，也不能覆盖所有并发交错。
