# 第七篇自测：协议收敛（7.1～7.4）

先独立回答，再对照后面的参考答案。建议画出发送方、驱动、接收方三个位置，标明对象或事件属于哪个上下文、哪个线程。

## 题目

1. 7.1 删除 CREATE_NODE 后，用户态怎样使驱动创建 Node？重复发送同一对象会发生什么？
2. 同一包先发送新的 LOCAL，再发送无效 fd。失败时要回滚哪些数据？为什么不能删除所有同 cookie 的 Node？
3. 7.2 为什么删除 `target_node`，却仍保留驱动内部的 `node_id`？
4. 管理者查找服务时，能否把自己保存的 handle 数字作为普通整数返回给客户端？应如何返回？
5. 普通调用线程没有进入 looper，READ 能否取得自己的回复？另一个线程能否领取该回复？
6. 同一线程既有自己的未交付回复，所在进程又有普通请求，7.3 的 READ 会先返回什么？消费后还需做什么？
7. ENTER_LOOPER、EXIT_LOOPER、THREAD_EXIT 和 FREE_REPLY 分别改变什么？ENTER 是否会创建 Linux 线程？
8. 到 7.3，哪些机制已经接近 Android Binder 的概念，哪些协议与生命周期机制仍有差异？
9. 7.4 的写阶段是否还等待回复？READ 交付回复前，需要完成什么状态转移？
10. WRITE_READ 的写阶段已成功、读阶段失败，为什么要保留 write_consumed？ServiceManager 怎样利用“回复后读取”组织响应循环？

## 参考答案

1. 在请求或回复中放入 LOCAL(cookie)。驱动以发送方上下文和非零 cookie 查找 Node，没有才创建；重复发送复用 Node，并在接收方复用对应 Ref。
2. 删除本次新建的 Node，不提交临时 Ref 表，释放本次取得的文件引用。既有 Node 或其他上下文的同 cookie 对象不属于本次失败创建，不能删除。此回滚范围不等于完整交付生命周期回滚。
3. 删除公开的全局寻址旁路，使普通调用必须经过调用方 Ref 表。内部仍可用 ID 关联 Node；内部存储方式和公开寻址协议是两个问题。
4. 不能。普通整数不会触发对象转换。应返回 HANDLE 对象，由驱动解析管理者 Ref，并在客户端上下文创建或复用其自己的 Ref。
5. 能。回复归原调用线程，与普通请求资格无关；其他线程不能读取该线程的 pending_reply。
6. 先返回 BR_REPLY；读取映射数据后发送 BC_FREE_REPLY，再 READ 领取进程请求，处理完用请求 id 提交 BC_REPLY。
7. ENTER/EXIT 改变当前线程接收普通请求的资格；THREAD_EXIT 显式清理线程记录和残留回复；FREE_REPLY 只释放当前回复缓冲区与未安装的文件引用，不替应用关闭已安装 fd。Linux 线程由用户态自行创建。
8. 自动 Node 创建、handle 寻址、looper 和统一 BR 分发已经相近；本章仍分离 WRITE/READ、每次固定一包、同步 WRITE 等待、固定槽位和教学对象描述符。未实现原生事务栈、引用计数、allocator、自动线程池扩容、oneway、安全策略及死亡通知，不能与 AOSP 二进制协议混用。
9. 写阶段只提交并入队。读阶段发现线程事务完成后，取走其回复工作，复制进回复映射并释放事务槽，再交付 BR_REPLY；回复映射位置保留至 FREE_REPLY。
10. 已成功提交的事务可能已经执行，清零重发会重复调用。保留进度只重试未完成阶段；但信号取消等错误有不同语义，不能一概重试。管理者用同一次 WRITE_READ 先提交上一条 BC_REPLY，再等下一条 BR_TRANSACTION，第一次则提交 ENTER_LOOPER 并等事件。
