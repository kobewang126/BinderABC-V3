# 教学接口的演进与退出点

独立章节保留当时的完整源码，便于观察设计如何变化；同一实验只能使用本章的驱动、头文件和程序。下面列出临时做法及其退出点，不表示历史版本已经与 Android Binder 兼容。

| 临时做法 | 为什么先这样实现 | 何时退出 |
| --- | --- | --- |
| 固定加法请求与专用事务 ioctl | 先把请求、等待和回复跑通 | 2.3～2.5 使用通用事务数据，2.6 用 BC/BR 替换事务专用操作 |
| 单事务槽 | 先理解同步调用，避免同时讲缓冲区分配 | 2.7 改为两个固定槽；仍不是通用 allocator |
| 显式 CREATE_NODE | 3.2 先观察 Node 身份；后续实验暂用创建结果引导通信 | 7.1 删除 ioctl、参数结构及全部调用，LOCAL 首次传递时创建，重复则复用；7.2～7.4 不再沿用 |
| 用户态直接填写 target_node | 暂时绕开“第一个引用从哪里来”的引导问题 | 4.4 引入管理者入口；7.2 删除公开字段，普通调用只用发送方 handle |
| REGISTER_SERVER 与固定服务端身份 | 最早用角色决定谁接收请求 | 4.3 删除；是否提供对象不再由角色决定 |
| READ_REQUEST / READ_REPLY | 4.3 先明确双向上下文的读取意图 | 7.3 删除，统一 READ 返回 BR_TRANSACTION 或 BR_REPLY |
| 公开事务 id、按 id 回复 | 早期用编号关联请求与回复；5.3 先专注调用线程的回复隔离 | 5.4 删除公开 id，服务线程绑定当前事务，回复沿 caller 返回；后续沿用，5.2 通过正常双服务线程实验串起调用链 |
| 独立 WRITE / READ，WRITE 等待回复 | 2.6 先分开讲提交命令和领取事件 | 7.4 统一 WRITE_READ，写阶段提交，读阶段等待和交付 |
| 显式线程退出 | 回归代码保留线程状态和回复位置的回收保护 | 当前仍保留；没有承诺自动处理任意线程死亡 |

## 为什么不在 3.4 就撤掉 CREATE_NODE？

3.4 首次讲 LOCAL→HANDLE，确实可以同时实现自动创建。但现有 3.5～6.4 的多进程实验用创建结果中的 Node 编号找到首次通信对象。若提前删除，必须同时重写这些实验的引导方式，容易把“对象转换”和“服务发现”一起塞进第三篇。

本版选择让 3.2 的显式登记先服务于可观察的独立实验；到 7.1，已有管理者和 handle，再统一取消登记。读者只需在早期理解它是教学脚手架，后续用户态封装以 7.4 为基础，不再沿用该接口。

## 几个字段分别回答什么问题？

| 字段 | 回答的问题 |
| --- | --- |
| cmd | 对驱动做什么：提交事务、提交回复、释放回复，或领取到了哪种事件？ |
| code | 目标用户态对象执行哪个方法，例如加法或查询服务？ |
| id（仅至 5.3） | 早期回复对应哪一笔事务？5.4 起由服务线程的 current_transaction 回答，不再是公开字段 |
| handle | 当前发送方上下文通过哪个 Ref 寻址目标对象？ |
| cookie | 对象拥有者用什么本地标识找回用户态对象？ |
| object_offsets | 负载中的对象描述分别从哪个字节位置开始？ |
| data_address | 接收方应从自己的哪个用户态地址读取请求数据？ |
| reply_offset | 当前教学实现中，从本进程映射基址的哪个位置读取回复？ |

对象位置表与映射地址不是一回事；id、方法 code 与协议 cmd 也不能互相代替。字段应在对应章节按需要学习，不必在开始时背下整张表。

## 最终边界

7.4 把本书的注册、查询、对象调用和通信入口收敛到一起，但仍采用固定容量与简化生命周期，没有实现原生 Binder 的事务栈、完整引用计数、安全策略或命令流兼容。后续 Framework 封装复用它的对象与 Parcel，不把这些简化接口当作 Android ABI。
